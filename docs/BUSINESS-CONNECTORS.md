# Business connectors

The business module is a server-side, owner-scoped read layer. It uses the existing `Store` records table and AES-256-GCM vault. Provider credentials never go to the Expo client or a model prompt. The module does not initiate payments, send mail, alter accounting records, or claim a provider is connected because a key happens to be configured.

## Mounting

Create `new BusinessService(store, config)`. Mount `businessCallbackRoutes(service)` at `/api/business` **before** the existing bearer-session middleware, and `businessRoutes(service)` at `/api/business` **after** that middleware. The callback consumes a short-lived, single-use state record and does not serve private data. `businessTools(service)` provides a host-neutral, owner-scoped callable contract. The separate stdio MCP bridge below makes the tools usable from Hermes through the same owner authentication.

The authenticated API provides `GET /connections`, `GET /capabilities`, `POST /connections/:provider/connect`, `POST /connections/:provider/verify`, `GET /connections/:provider/status`, `POST /connections/:provider/disconnect`, `POST /connections/square/token`, `POST /connections/xero/tenant`, `POST /connections/:provider/complete`, `POST /sync`, `GET /entities`, and `GET /observation`. `/sync` takes `{provider,kind,cursor?}` and fetches **one page**. Follow `nextCursor` until null; keep the cursor with its provider, capability, and connection ID. It returns the saved page facts and exact source evidence. `verificationFresh` reports whether identity was checked in the last 15 minutes. `verifiedAt` and `lastSyncAt` are separate milestones.

## Hermes and proactive observation

Register the stdio MCP server in Hermes's Oracle profile with command `node C:\OpenMuseBusinessOS\app\dist\apps\server\src\business\mcp-server.js` after building the server. During development use `pnpm exec tsx apps/server/src/business/mcp-server.ts` from the repository. Give that process only `BUSINESS_API_URL` (the private HTTPS OpenMuse API) and `OPENMUSE_ACCESS_KEY` (the owner access key). Keep the key in Oracle's private environment or Hermes secret configuration, never in the profile committed to Git. The bridge signs in at `/api/session`, keeps the bearer token in process memory, and exposes `business_capabilities`, `business_connections`, `business_observation`, `business_entities`, and `business_sync`. It accepts HTTPS, or HTTP only to local loopback. These tools only read provider APIs; `business_sync` stores a local snapshot. Hermes must register this MCP server explicitly in its profile; an OpenMuse route alone does not make tools available to Hermes.

On the single process running the existing durable task worker, call `business.start(agent)` after `agent.start()` and `await business.stop()` before closing the database. The default interval is five minutes. It scans only verified owner connections, reads each source's latest page and advances one persisted backfill cursor per poll. A source's first page establishes a baseline. Subsequent changed facts from one provider capability poll create one idempotent `agent` task through `AgentService.createTask`; they use the existing task worker and memory flow, not a second queue. Unseen historical backfill is stored without announcing it as new activity. A source fact's title, status, amount, currency, event time, provider update time, invoice due/paid amounts, or contact details can trigger a changed task; changes to fetch time alone do not. If the provider read fails, no fresh fact or task is claimed. Run this observer in one process only when using a separate API and worker.

## Provider setup and coverage

| Provider | Server configuration | Identity verification | Read capabilities |
| --- | --- | --- | --- |
| Square | `SQUARE_ACCESS_TOKEN` or `SQUARE_CLIENT_ID` + `SQUARE_CLIENT_SECRET`; encrypted token submission also supported | Live `GET /v2/merchants` | Merchants, locations, paged payments across every returned location |
| Xero | `XERO_CLIENT_ID` + `XERO_CLIENT_SECRET` | Live Connections followed by the selected tenant's Organisation | Organisation, accounts, paged bank transactions, sales invoices, purchase bills, contacts |
| Revolut Business | `REVOLUT_CLIENT_ID` + `REVOLUT_PRIVATE_KEY_FILE` (private PEM readable only by the server) | Live `GET /accounts` | Balances and time-paged transactions |
| Google Workspace | Existing local `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TOKEN_ENCRYPTION_KEY` and `GoogleAuth` flow | Live Gmail profile | Paged Gmail message references |

All provider connections require the existing `TOKEN_ENCRYPTION_KEY` for stored OAuth/token credentials. Keep app secrets and the Revolut private key outside the repository. Square's environment token is read from the server environment; the private file in another workspace is not imported automatically. The supplied Square token was independently checked with a read-only merchant request on 2026-09-23; that observation does not configure a deployed server. Google uses the existing local OAuth credential, not a Codex or Claude connection. Xero, Square, and Revolut require their own app consent flows. Xero refuses to guess when multiple tenants are authorized; select one explicitly. New Xero consent requests granular read scopes `accounting.settings.read`, `accounting.banktransactions.read`, `accounting.invoices.read`, and `accounting.contacts.read`; the capability list hides invoice/contact reads when an existing token lacks those scopes, and the owner must reconnect to grant them. Revolut's published `app-confirm` guide does not promise a returned `state` parameter, so its authenticated `/connections/revolut/complete` path accepts the code and original state when the callback cannot validate state automatically.

The business data lives in `business-connections`, `business-facts`, `business-syncs`, and `business-watch-*` kinds in the existing `records` table. No schema migration is required. Facts carry provider, source ID, connection ID, fetch timestamp, source timestamp where supplied, endpoint, currency and provider amount representation. Square supplies integer minor units. Xero and Revolut supply decimal values; the code stores their textual representation without sums or conversion. Xero invoice facts identify `ACCREC` sales invoices versus `ACCPAY` bills and retain the document number, contact ID/name, total, amount due, amount paid, and due date. Contacts retain Xero ID, name, optional email and customer/supplier flags; bank account details are not copied into these facts. Xero invoice and contact pages explicitly sort by latest update, because Xero defaults to oldest first. Xero's `DateString`/`DueDateString` may omit a timezone and are preserved verbatim, so the UI must not infer one. A multi-leg Revolut transaction does not get a misleading single amount. Old facts are retained but omitted from current entity/observation results after account reconnection. The API does not equate Square payments, Xero bank transactions, and Revolut transactions or assert settlement without a reconciliation rule. Removing a source record is not currently inferred from absence on a later paged read. Square's default payment history window is the preceding year; this connector has no earlier-history range selector yet. Revolut time-boundary pagination should be reviewed if more than 1,000 records share a provider timestamp.

Only GET provider calls are retried on rate limits or transient server errors. Token exchanges and refreshes are never automatically retried after an uncertain response. Local writes upsert facts by provider ID, so replaying a sync page does not duplicate facts. Live provider calls, OAuth consent, and actual provider data are needed before any business result can be described as current.
