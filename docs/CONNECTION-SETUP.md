# Direct connection setup for Oracle

Use the deployment's live API origin, represented here as `https://oracle.your-tailnet.ts.net:10001`. Replace the hostname with the actual tailnet hostname and configure provider applications against that **exact** origin; if it changes, update `PUBLIC_API_URL`, the client build URL, and every registered redirect URI together. Provider secrets belong only in `C:\OpenMuseBusinessOS\app\.env` or `C:\OpenMuseBusinessOS\secrets`, under the deployment's private Windows ACL. `TOKEN_ENCRYPTION_KEY` must remain set because the API encrypts saved OAuth tokens. A configured app is not a verified provider connection: finish consent from OpenMuse's Apps screen and check its connection status and identity.

## Google Workspace

Create an OAuth **web application** in the owner's Google Cloud project, enable the Gmail API and Google Calendar API, configure the consent screen and allowed owner/test user, and add the exact Google redirect URI above. This API's initial connection requests `gmail.readonly`, `calendar.events.readonly`, and `calendar.calendarlist.readonly` as full `https://www.googleapis.com/auth/` scope URIs. The optional write-upgrade flow additionally requests `gmail.send` and `calendar.events`; choose it only if sending mail and editing events are wanted. The application requests offline access so its encrypted refresh token can support subsequent reads. Gmail read access is a [restricted scope](https://developers.google.com/workspace/gmail/api/auth/scopes), so Google may require verification or impose testing-mode limits depending on the consent-screen audience. A Codex-managed Gmail connection or its token cannot be reused as this app's OAuth client. See Google's [web-server OAuth redirect requirements](https://developers.google.com/identity/protocols/oauth2/web-server), [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), and [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth).

## Xero

Create a Xero OAuth 2.0 app using the **Auth Code** grant and save its Client ID and Client Secret privately on Oracle. Register the exact Xero callback above. The connector requests these space-separated scopes: `offline_access openid profile accounting.settings.read accounting.banktransactions.read accounting.invoices.read accounting.contacts.read`. They cover organisation/accounts, bank transactions, sales invoices and purchase bills, and contacts. `offline_access` is needed for refresh tokens. After consent, select the correct Xero organisation if more than one tenant was authorized; the connector does not pick one by guess. Prior Codex-managed Xero authorization does not supply this app's client credentials or tenant grant. See Xero's [authorization-code flow](https://developer.xero.com/documentation/guides/oauth2/auth-flow) and [scope catalogue](https://developer.xero.com/documentation/guides/oauth2/scopes).

## Revolut Business

The public X.509 PEM upload file is `C:\OpenMuseBusinessOS\secrets\revolut-public.cer`. The matching unencrypted RSA-2048 private key is `C:\OpenMuseBusinessOS\secrets\revolut-private.pem`; it stays on Oracle and must never be uploaded or pasted into a prompt. The Oracle generator is `scripts/oracle/prepare-revolut.py`, run with the existing `C:\OpenMuseBusinessOS\runtime\hermes-venv\Scripts\python.exe`. Run it with `--public-url https://oracle.your-tailnet.ts.net:10001` after replacing the placeholder hostname. It uses exclusive file creation, validates an existing pair, and will not overwrite a private key. Keep the private file under an ACL limited to the deployment owner, SYSTEM, and Administrators.

In Revolut Business, use **Settings → APIs → Business API → Add API certificate**. Paste the entire public certificate, including `BEGIN/END CERTIFICATE`, into the X509 public-key field. Enter the exact Revolut callback above and retain the returned `ClientID` in `REVOLUT_CLIENT_ID`. The connector requests only the `READ` consent scope, then verifies identity through a live accounts read. The server signs client assertions with `RS256`; its `iss` is the callback **hostname** `oracle.your-tailnet.ts.net` without scheme or port, `sub` is the Revolut Client ID, and `aud` is `https://revolut.com`. Revolut requires the redirect domain and JWT issuer domain to match. Its documented consent redirect does not guarantee an OAuth `state` parameter; if Revolut returns only `code`, use the authenticated OpenMuse completion flow while its original short-lived state is still valid. See Revolut's [Business API certificate and first-request guide](https://developer.revolut.com/docs/guides/manage-accounts/get-started/make-your-first-api-request).

## APNs for native notifications and calls

The server requires `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`, and `APNS_PRIVATE_KEY_PATH` to a valid Apple `.p8` signing key. The app's iOS bundle identifier is `au.com.wineandlarder.openmuse`. On 24 September 2026, its team, push capability, distribution entitlement and existing APNs key were verified against the Apple Developer account and signed device build. Both production device registrations reached Oracle; Apple accepted an ordinary alert and a genuine incoming-call push. The owner confirmed that call rang and was answered, but audio failed and ordinary alert visibility is still unconfirmed. A separate App Store Connect API key is not an APNs signing key. The server sends alert notifications under the bundle topic and VoIP pushes under the `.voip` topic. See Apple's [token-based APNs connection guidance](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns) and the [remaining physical acceptance checks](../apps/mobile/docs/IOS-CALLING.md).

These instructions prepare the account-side fields; they do not create provider apps, grant OAuth consent, or validate APNs delivery. Once the owner completes those provider-side steps, OpenMuse must show the verified identity and fresh status before its business facts are considered live.
